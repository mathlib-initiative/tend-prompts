# tech-debt-reduction

Prompts for running a Tend swarm as a **technical-debt reduction campaign** on an
existing codebase: pay debt down without changing what the code does, and prove
each removal actually left the tree instead of moving somewhere invisible. A
contribution repairs an upstream root cause, deletes the workarounds that root
unblocked, and moves the debt tracker and the human debt log to match — with the
build still green and the hole census still zero. The reviewer's single job is the
one thing no automated gate can do: decide whether the debt the worker *claims* to
have removed was really removed, and whether the reported numbers are honest.

The suite encodes a debt-management discipline built over months on a large
formal-mathematics codebase (Lean 4 / Mathlib). The practice is battle-tested;
these prompts, as a Tend suite, are new and unrun — see Evaluation, and treat the
status accordingly. Project-specific values are marked `<<LIKE_THIS>>` and must be
replaced before use; Tend does not expand them.

## Purpose

Use this suite when:

- the codebase already builds and passes, and the goal is to **reduce tracked
  debt** (workarounds, suppressions, duplication) rather than to add features or
  fix failing tests;
- there is, or you will stand up, a **deterministic debt tracker** that scans the
  source and emits priced, dependency-ordered counts as a delta from a pinned
  baseline — the numbers in this suite come from that tracker, not from estimates;
- a **hole census** (code that lies about being done) can be enforced at zero, so
  that "make it pass" can never be achieved by hiding work;
- faithfulness of the *count* matters as much as the cleanup — the value is a
  debt record you can trust, paid down in small, reviewable, reversible steps.

A different suite is more appropriate for building features, for fixing a red
build or failing tests (here the build is assumed green before work starts), or
for a formalization/authoring project where the reviewer's job is semantic
fidelity to a source text rather than debt accounting (see `lean-formalization`).

## Assumptions and configuration

- **Status: draft.** The underlying debt-management practice ran for months on a
  real project (below), but these worker/reviewer prompts have not themselves been
  run as a Tend suite. Try them on a small scope and record results before relying
  on them.
- Runner: Tend's generated `--agent tend` scripts.
- Repository/task assumptions. The prompts expect, in the target repository:
  - `AGENTS.md` at the root: the working agreement (layout, build/validate
    commands, the **exact** hole and suppression marker sets for this repo, the
    debt policy). The prompts defer to it so policy can change without editing
    prompts — the marker tiers in the prompts are a portable default, not a
    substitute for the repo's precise definitions.
  - A **deterministic debt tracker** regenerated by `<<TRACKER_CMD>>`: a pure
    function of the source that emits per-unit and whole-tree counts as a delta
    from the pinned baseline `<<BASELINE_REF>>`, plus a curated annotations layer
    keyed by symbol/basename (not file path) so it survives renames. Two runs must
    produce byte-identical output.
  - A **human debt log** at `<<DEBT_LOG>>`: principles, a per-area ledger of *why
    each item exists and what would remove it*, and a running log of cleanup
    rounds. It links to the generated numbers rather than restating them.
  - A fast **hole census** `<<CENSUS_CMD>>` — a pure source scan, sub-second — whose
    clean output is exactly `<<CENSUS_OK>>`, and a full gate `<<VALIDATE_CMD>>`
    (census first, then build) wired as Tend's pre-review **and** pre-merge
    validation command, so no merge can land a non-zero census.
  - A single-unit build command `<<BUILD_CMD>>` that fits inside the bash tool's
    600-second cap (a full project build generally does not).
  - Task YAML that scopes a debt area or class and a definition of done. Task ids
    may differ from filenames; the prompts resolve by id.
- Required tools: whatever `<<VALIDATE_CMD>>`, `<<CENSUS_CMD>>`, `<<BUILD_CMD>>`
  and `<<TRACKER_CMD>>` invoke (in the original project: `lake`, `python3`, `git`).
- Model or runtime requirements: used with a frontier model for workers; the
  compiler-decides removal loop and the absorber test are iterative, so workers
  need a generous per-task wall-time and output budget. A reviewer that actually
  re-runs the absorber test and regenerates the tracker needs tool access and a
  comparable timeout, not a quick skim.
- Tend compatibility: the environment-variable, discussion-path, and
  `final_result` conventions of this repository's README. No worker/reviewer run
  of this suite has been recorded; validate against your Tend version with a dry
  run before a live campaign.

| --- | --- | --- |
| `<<VALIDATE_CMD>>` | The full gate (hole census first, then build) wired as pre-review and pre-merge validation | `bash scripts/slop-gate.sh` (the project also used a stricter `scripts/validate.sh`) |
| `<<CENSUS_CMD>>` | The fast, pure-source hole census | `python3 scripts/sorry_check.py --list \| tail -1` |

### What the prompts encode, briefly

- **The absorber test is the center of gravity.** A workaround that still compiles
  after deletion is not necessarily gone — a removal counts *only* if nothing was
  added to compensate. Both the worker (before claiming) and the reviewer (against
  the diff) apply it; a removal that needed a cast, helper, alternate suppression,
  or raised budget is debt that moved, not debt that left.
- **Let the compiler decide, never guess.** Delete → rebuild the unit → re-add only
  where the toolchain objects → iterate. No heuristic about which sites are "probably
  safe".
- **Bottom-up by root cause, bundled, high blast-radius first.** Fix the upstream
  definition so the downstream workarounds become droppable; one contribution per
  root cause tells a reviewable story.
- **Measure, don't guess; correct your numbers out loud.** Reported deltas are the
  deterministic tracker's numbers against the pinned baseline, never estimates; the
  tracker and `<<DEBT_LOG>>` move in the *same* contribution; a wrong figure is
  restated, not quietly fixed.
- **Never buy greenness with a hole.** No marker in `<<HOLE_MARKERS>>`, no stubbed
  return, no disabled test, no type-system escape — even where the gate would
  tolerate it. `blocked` with a precise account beats a false "removed".
- **The reviewer's job is the debt accounting, not the build.** The gate already
  proved it compiles and the census is zero; the reviewer re-runs the absorber
  test, checks the numbers against the tracker, confirms the record moved, and
  checks nothing was hidden — and does *not* reject a workaround the worker
  honestly left as attempted-and-kept.

## Evaluation and provenance

Derived from the technical-debt tracker, gate, and cleanup discipline of the
CFT_clean project — a ~1,250-file Lean 4 / Mathlib formalization ported and
maintained by a Tend swarm — written by the project's operator in 2025–2026. The
prompts themselves are **new**: they translate that project's `TechDebt.md`
(principles and per-area ledger), its deterministic dashboard generator, its
hole census and merge gate, and its month-long cleanup campaign into Tend
worker/reviewer form. No third-party prompt text is included.

Evidence is for the **underlying practice**, not for this suite as run:

- The debt tracker was a deterministic, baseline-delta generator with a
  symbol-keyed curated annotations layer and a resolved-detector; it emitted a
  machine summary and a human index from one command, proven byte-identical across
  runs under varied hash seeds.
- The gate enforced a whole-tree hole census of zero (sorry/axiom and kin) before
  every merge and as a cold from-scratch audit; a holed change can compile, so the
  census ran first and fast.
- The absorber test was a measured filter, not a slogan: in one cleanup pass it
  rejected 65 of 121 candidate removals that all compiled green, because deleting
  them required a compensating change — the debt would have moved, not left.
- A toolchain bump made 6 of 7 performance workarounds obsolete and let 5 more be
  deleted, which is why the suite insists on a green baseline before cleaning and on
  letting the compiler, not a heuristic, decide each removal.
- The "measure, don't guess" rule is from a real correction: a migration first
  reported as "+1 workaround" was re-measured against the whole-tree counter and
  the honest figure was **+3**; the number was restated out loud, not quietly fixed.

Observations that bear on the prompts:

- The reviewer is deliberately narrow and adversarial. On a sibling project a
  checklist-walking reviewer approved 230 of 236 contributions while the real
  semantic defects were caught by cross-cutting audits, not per-contribution
  review. A reviewer with one sharp question — *did this debt actually leave?* —
  is likely to do better than one walking a long list.
- The tracker is the contract. Every number in the prompts is the tracker's,
  because a hand-copied count drifts (a hand-maintained file/count table once
  disagreed with the scanner within a day) and a delta quoted across a change in
  the counting unit reads as a regression that never happened.
- Holes and suppressions must be defined precisely for the repo and encoded in the
  scanner; the marker tiers in the prompts are a portable default, and the real
  definitions belong in `AGENTS.md` and the scanner, where they fire.

No evaluation of this suite as a Tend run has been recorded.
