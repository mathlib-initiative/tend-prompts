# Tend prompt suites

Collections of prompts for using Tend on different kinds of work. A **suite**
keeps a worker's instructions, its revision workflow, and the reviewer's criteria
together so they can be selected and changed as a unit.

Browse the [suite catalogue](suites/README.md), or start a new suite from the
[authoring template](templates/suite/README.md). No task-specific suites have
been added yet.

## Repository layout

```text
suites/
  README.md                  # Catalogue of available suites
  <suite-name>/
    README.md                # Purpose, assumptions, compatibility, and evidence
    prompts/
      worker-system.md
      worker.md
      worker-revision.md
      reviewer-system.md
      reviewer.md
templates/
  suite/                     # Copy this directory to start a suite
```

Use short, descriptive, lower-kebab-case suite names based on the work, such as
`lean-formalization` or `documentation-maintenance`. These are naming examples,
not existing suites. Keep each suite self-contained; Tend does not expand
Markdown links or include shared prompt fragments automatically.

Use Git history to version a suite. Create another suite when its purpose or
workflow differs enough to be independently useful. Record the suite path and
repository commit when running an experiment, along with any local edits.

## Prompt roles

The filenames match the files generated by `tend init --agent tend`:

| File in `prompts/` | When used | What belongs here |
| --- | --- | --- |
| `worker-system.md` | Every worker launch, including revisions | Role, scope, working conventions, and output contract. |
| `worker.md` | Initial assignment; also the fallback when no revision prompt is available | How to locate and carry out the assigned task, validate it, and report the result. |
| `worker-revision.md` | Resumed worker session with pending reviewer or orchestrator feedback | How to address feedback and validate the revised contribution. |
| `reviewer-system.md` | Every reviewer launch | Review responsibilities, standards, and output contract. |
| `reviewer.md` | Each review invocation | What to inspect and how to reach an actionable verdict. |

The worker reuses its system prompt during revisions; there is no separate
revision-system slot in the generated setup. A task prompt describes how to
handle an assignment. Actual task definitions remain YAML files under `tasks/`
in the repository Tend is working on.

## Add a suite

From this repository's root:

```bash
cp -R templates/suite suites/my-suite
```

1. Fill in the suite README: intended work, assumptions, required tools, Tend
   compatibility, and any evaluation evidence.
2. Edit all five prompts and replace every `TODO`. Keep worker instructions and
   reviewer criteria consistent. The template is an authoring scaffold, not an
   evaluated suite.
3. Check the prompt conventions below and try the suite on representative tasks.
   Record what was actually checked; leave unmeasured results as unknown.
4. Add the suite to the [catalogue](suites/README.md), with its status and purpose.

Suites may add an `examples/` directory for illustrative task YAML or a document
describing evaluation results. These are supporting material, not automatically
loaded prompts. Keep model selection, tool permissions, budgets, and build
commands in Tend's configuration; document any requirements in the suite README.

## Use a suite with Tend

After authoring a suite, initialize a new orchestration root with Tend installed
and available on `PATH`. Keep that root outside the target repository. Replace
these example absolute paths with your own:

```bash
TEND_RUN_ROOT=/absolute/path/to/new-tend-run
TEND_TARGET_REPO=/absolute/path/to/project
TEND_PROMPT_SUITE=/absolute/path/to/tend-prompts/suites/my-suite

tend init --root "$TEND_RUN_ROOT" --entrypoint "$TEND_TARGET_REPO" --agent tend
cp "$TEND_PROMPT_SUITE"/prompts/*.md "$TEND_RUN_ROOT/prompts/"
tend validate-config --root "$TEND_RUN_ROOT"
tend run --root "$TEND_RUN_ROOT" --dry-run
```

The copy replaces the newly generated default prompts. Review the generated
agent/model configuration, configure the project's validation commands, and
prepare committed task files before a live run. Configuration validation and a
dry run do not evaluate prompt quality. See Tend's orchestrator quickstart for
the rest of run setup.

Tend reads these files on subsequent agent launches. Copying makes a run's
prompts independent of later edits to this checkout. To update an existing run,
stop it first, preserve its current prompts, and copy the chosen suite before
resuming.

This layout is a repository convention. Tend does not discover this catalogue
or load a suite by name. Its `--worker-prompt-version` and
`--reviewer-prompt-version` flags select variants in Tend's bundled prompt
registry; installing these suites uses the file copy above.

## Prompt conventions and compatibility

Write plain UTF-8 Markdown in the form consumed by the generated launchers:

- Refer to Tend's environment variables, such as `$TEND_TASK_ID`,
  `$TEND_WORKTREE_PATH`, `$TEND_WORKTREE_ID`, and `$TEND_AGENT_DISCUSSION_PATH`.
  These references are instructions for the agent to resolve using its tools;
  the launcher does **not** interpolate their values in the prompt text. Find
  the task YAML by its `id`, which need not match its filename.
- Keep the literal `{feedback_message}` marker in `worker-revision.md`. Tend
  replaces it with the latest pending non-worker discussion message before a
  resumed worker launch. Tell the worker to consult the discussion log for
  context as well.
- Do not use `{task_path}`, `{worktree_path}`, or `{contribution_id}` in copied
  prompts. Those are placeholders in Tend's bundled source prompts, rendered
  during `init`; copying a suite does not run that renderer. Other braces,
  including JSON examples, remain literal.
- Preserve the generated `final_result` contracts. Workers return
  `schema_version: 1`, a `status` of `completed`, `blocked`, or `needs_review`,
  and a non-empty `summary`. Reviewers return `schema_version: 1`, `verdict` of
  `approve` or `request_changes`, and non-empty `notes`. A `request_changes`
  verdict requires non-empty `feedback_text`; an `approve` verdict must omit it.
- Workers commit their changes in the assigned worktree; Tend handles merging.
  Reviewers inspect and report without merging. Prompts should make the suite's
  completion and review criteria explicit.

The initial convention was checked against Tend commit
`2143096c072a6457b0cf973ed2a64bd67757d66d`, specifically
`src/tend/orchestrator/cli.py`, `src/tend/orchestrator/agent_runner.py`,
`src/tend/_common/agent_outputs.py`, and `docs/orchestrator/agents.md`.
Record compatibility and testing separately in each suite's README.

The template targets `--agent tend`. Tend's generated `--agent pi` scripts do
not select `worker-revision.md` or provide Tend's `final_result` tool; a Pi or
custom-runner suite must document its own adaptation and satisfy the same
worker/reviewer JSON output schemas. Additional prompt roles need explicit
consumer support before they can participate in a run.
